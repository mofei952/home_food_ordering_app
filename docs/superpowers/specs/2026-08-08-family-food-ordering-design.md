# 家庭点菜 PWA 产品设计

- 状态：已批准
- 日期：2026-08-08
- 首期对象：单个验证家庭
- 产品形态：移动优先的 PWA

## 1. 背景与目标

家庭成员都会做饭，也都会参与点菜。当前主要问题不是缺少菜谱，而是每天需要反复讨论“吃什么”，已有食材、每个人会做的菜和近期吃过的菜也没有集中呈现。

首版建立一个家庭私有菜品库，让成员为指定日期的午餐或晚餐提交想吃的菜，再由任一成员确认最终菜单。不知道吃什么时，可以筛选后随机选择，或者临时勾选家中食材查找可做的菜。

最高优先级目标是减少决定吃什么所需的时间，而不是提供完整的烹饪、营养或库存管理服务。

### 1.1 成功标准

在同一个家庭中连续试用两周，并达到：

- 至少 70% 的家庭用餐通过应用确定菜单。
- 从打开餐次页面到确认菜单的中位时间不超过 3 分钟。
- 每周因“吃什么”产生的线下反复讨论不超过 2 次。

最后一项由每周一次的家庭问卷收集，不能仅凭应用事件推断。

## 2. 用户与使用场景

### 2.1 家庭模型

- 多位成员都会做饭，也都会点菜。
- 不预先指定某餐的做饭人。
- 任一成员均可确认或修改最终菜单。
- 成员通过 8 位邀请码加入家庭，并使用昵称和 4–6 位数字 PIN 区分身份。
- 家庭创建者仅负责成员管理：刷新邀请码、停用成员或重置成员 PIN；该身份不影响点菜和菜单权限。

### 2.2 核心场景

1. 成员录入自己或其他成员会做的菜。
2. 成员为某日午餐或晚餐提交任意数量的想吃菜品。
3. 任一成员综合所有请求并确认最终菜单。
4. 不知道吃什么时，按制作者、类别或食材筛选后随机选择。
5. 临时勾选家中现有食材，查找现在能做或只缺一种主料的菜。

## 3. 市场调研

本阶段不验证商业化市场，调研目的仅是确认需求存在、识别可借鉴模式并避免首版范围膨胀。公开资料于 2026-08-08 查阅。

### 3.1 国内产品

- [下厨房](https://www.xiachufang.com/)、[豆果美食](https://www.douguo.com/)和[香哈菜谱](https://www.xiangha.com/)以海量菜谱、搜索、内容社区和烹饪学习为核心。它们擅长回答“这道菜怎么做”，但家庭成员围绕自家菜品库协作点菜并非其主要产品流程。
- [点菜吧·亲爱的！](https://2juan.com/)将“选菜或一键生成—菜单—采购清单”作为主要流程，直接聚焦“今天吃什么”的决策成本。
- [饿不死 Erbusi](https://caishu.online/)侧重 AI 周菜单、食材生成菜品和健康管理，说明家庭膳食决策存在需求，但其自动规划和健康定位不适合作为本项目首版重点。
- 开源项目 [yiohyi 家宴菜谱小程序](https://github.com/C-wj/yiohyi)包含家庭成员协作、按餐次点菜和购物清单，证明“家庭私有菜谱 + 点菜”可以形成完整流程。

### 3.2 海外产品

- [Mealisto](https://mealisto.com/)、[FamilyPlate](https://www.familyplate.ai/)、[PlanMeals](https://planmeals.app/)和[Dinna](https://getdinna.app/)普遍采用家庭投票、周计划和购物清单，验证了共同决策的价值，但更偏向投票自动规划。
- [SuperCook](https://www.supercook.com/)围绕已有食材查找菜谱，验证了按食材匹配的实用性，但需要维护较完整的虚拟储藏室。
- [Mealie](https://github.com/mealie-recipes/mealie)提供家庭菜谱、周计划和购物清单，功能完整但更适合愿意自托管的技术用户。

### 3.3 产品定位结论

本产品不是另一个公共菜谱社区，而是“我家谁会做什么 + 今天这顿想吃什么 + 快速确认”的轻协作工具。

差异化组合是：

- 家庭私有菜品库；
- 按日期与午/晚餐协作点菜；
- 由人最终确认，而不是投票或 AI 自动决定；
- 在同一个家庭菜品库内进行随机和临时食材匹配；
- 以三分钟内完成决策作为明确指标。

## 4. 产品方案与范围

曾考虑三条路径：

1. 极简协作点菜板；
2. AI 膳食管家；
3. 公共菜谱社区加家庭空间。

首版采用第一条路径。它最直接验证核心目标，避免 AI、公开内容和复杂供应链功能掩盖真实需求。

### 4.1 首版必须包含

1. 创建家庭、邀请码加入、昵称和 PIN 身份。
2. 家庭私有菜品库。
3. 按日期和午餐/晚餐点菜。
4. 汇总成员请求并确认最终菜单。
5. 确认后继续修改，并显示最后修改人和时间。
6. 按条件筛选后的加权随机。
7. 临时食材匹配。
8. 历史菜单和最小验证指标。
9. 可添加到手机主屏幕的 PWA。

### 4.2 首版明确不包含

- 长期食材库存、扫码录入或购物同步；
- 采购清单和周菜单；
- 推送或外部渠道通知；
- AI 推荐、图片识菜、营养和健康建议；
- 完整做法步骤；
- 手机号、微信授权、公开社区、支付或配送；
- 完整离线写入和复杂实时协作。

## 5. 信息架构

移动端保留四个一级入口：

- **今天**：默认首页；切换日期和餐次，点菜并确认菜单。
- **菜品**：浏览、新增、编辑和归档家庭菜品。
- **帮我选**：随机点菜和按临时食材找菜。
- **家庭**：成员、邀请码、当前身份和历史菜单。

历史菜单使用频率低于每日点菜，因此归入“家庭”，不单独占用一级入口。

## 6. 核心流程

### 6.1 首次使用

```text
创建家庭 → 获得邀请码 → 家人加入 → 设置昵称和 PIN → 录入家庭菜品
```

验证开始前，建议全家合计录入 15–30 道常做菜，避免菜品库过小使随机和食材匹配失去意义。

### 6.2 每日点菜

```text
选择日期和午/晚餐
  → 成员提交想吃的菜
  → 形成想吃清单
  → 任一成员编辑并确认最终菜单
  → 记录历史与近期食用时间
```

餐次仅有三种状态：

- **未开始**：还没有成员点菜；
- **待确认**：已有点菜请求，但没有最终菜单；
- **已确认**：已有最终菜单，之后仍可修改。

### 6.3 随机点菜

用户可以先按以下条件筛选：

- 会做这道菜的成员；
- 荤菜、素菜、主食、汤等类别；
- 临时选择的已有食材。

筛选完成后按近期食用时间加权随机。结果只是一项建议，用户可以“就吃这个”加入当前餐次或“换一道”，系统不会自动确认菜单。

### 6.4 按食材找菜

用户临时勾选现有食材，不维护长期库存。结果分为：

1. **现在就能做**：主要食材全部具备；
2. **再补一种即可**：只缺一种主要食材；
3. 缺两种及以上：不显示。

油、盐、糖、酱油等常用调料默认具备，不参与匹配。

## 7. 业务规则

### 7.1 菜品

每道菜包含：

- 菜名；
- 一位或多位会做这道菜的成员；
- 至少一种主要食材；
- 类别；
- 可选图片；
- 创建人、最后修改人和时间。

同名菜允许存在，但界面必须显示制作者。已经被历史菜单引用的菜只能归档，不能物理删除。历史菜单保存当时的菜名和图片快照，后续编辑不会篡改旧记录。

### 7.2 点菜与菜单

- 每位成员每餐的点菜数量不设上限。
- 同一道菜被多人选择时，只展示一张菜品卡，并列出全部点菜人。
- 成员只能撤回自己的请求。
- 最终菜单可以添加未被请求的菜，也可以移除已被请求的菜。
- 任一成员均可确认和继续修改菜单。
- 页面显示最后修改人和时间。
- 修改按菜品逐项提交，降低多人同时操作造成整份菜单互相覆盖的风险。

不限点菜数量可能延长确认时间。验证期需要分析点菜数量与确认时长的关系；若目标未达成，再考虑首选标记或数量上限。

### 7.3 随机权重

先应用硬筛选条件，再按下表加权：

| 距上次食用时间 | 权重 |
|---|---:|
| 3 天以内 | 0.2 |
| 4–7 天 | 0.5 |
| 8–14 天 | 0.8 |
| 超过 14 天或从未吃过 | 1.0 |

如果筛选后没有候选项，系统提示用户放宽具体条件，不擅自忽略条件。

### 7.4 食材规范化

菜品录入时优先从统一食材词表选择，也允许补充新词。同义词需要映射到规范名称，例如“番茄”和“西红柿”应能匹配。首版只记录主要食材是否需要，不记录数量和单位。

## 8. 异常处理

- **网络中断**：保留尚未提交的输入，恢复网络后允许重试；不承诺离线协作。
- **重复提交**：客户端操作标识和数据库唯一约束共同避免重复请求或菜单项。
- **并发修改**：逐项更新；同一项发生版本冲突时获取最新状态并提示用户。
- **PIN 错误**：限制连续尝试频率。简单 PIN 仅用于家庭身份区分，不视为高强度认证。
- **图片失败**：不阻止菜品文本保存；接受 JPEG、PNG 或 WebP，原图不超过 10 MB，上传前压缩为最长边不超过 1600 像素且不超过 2 MB。
- **成员退出**：保留其菜品和历史记录，将成员状态改为已退出。
- **空菜品库**：引导录入菜品，不生成没有依据的随机结果。

## 9. 技术架构

采用独立前后端，但保持单体后端和单一关系型数据库：

```text
React + TypeScript + Vite PWA
              │ REST / OpenAPI
              ▼
          FastAPI 应用
    ┌─────────┼──────────┐
    ▼         ▼          ▼
PostgreSQL  对象存储   指标事件
```

### 9.1 技术选择

- 前端：React、TypeScript、Vite；
- PWA：Web App Manifest、Service Worker；
- 后端：FastAPI；
- 数据库：PostgreSQL；
- 数据访问和迁移：SQLAlchemy、Alembic；
- 图片：兼容 S3 的对象存储；
- 接口：REST API，以 OpenAPI 为契约；
- 测试：前端单元测试、浏览器端到端测试、后端 pytest。

前端 TypeScript 客户端由 OpenAPI 定义生成或校验，降低独立前后端之间的类型漂移。

首版不引入微服务、消息队列或 WebSocket。数据在提交后重新获取，页面重新获得焦点时自动同步；只有验证出强实时需求后才增加实时通道。

### 9.2 模块边界

- **家庭身份模块**：邀请码、成员、PIN 和会话；
- **菜品目录模块**：菜品、制作者、类别、主要食材和图片；
- **餐次模块**：日期、午/晚餐、点菜请求和最终菜单；
- **推荐模块**：根据候选菜、筛选条件和历史记录执行纯规则计算；
- **食材匹配模块**：规范化食材并计算缺失数量；
- **历史与指标模块**：保存菜单历史和验证事件；
- **图片模块**：上传、压缩和删除，与菜品文本保存解耦。

推荐和食材匹配模块不直接依赖 HTTP 或数据库，使规则可以独立测试和替换。

## 10. 数据模型

- `households`：家庭；
- `members`：成员、PIN 哈希和状态；
- `sessions`：成员会话；
- `dishes`：菜品基本信息及归档状态；
- `dish_cooks`：菜品与会做成员的多对多关系；
- `ingredients`：规范化食材和同义词；
- `dish_ingredients`：菜品主要食材；
- `meal_slots`：家庭、日期和午/晚餐，三者组合唯一；
- `meal_requests`：成员对餐次的菜品请求；
- `menu_items`：最终菜单及菜品快照；
- `activity_events`：确认、修改和验证事件。

所有家庭业务表都必须直接或间接绑定家庭标识，服务端每次访问均校验家庭范围。

## 11. 安全与隐私

- PIN 只保存加盐哈希，不保存明文；
- 登录后使用安全、HttpOnly、SameSite 会话 Cookie；
- 每个查询和写入均执行家庭数据隔离；
- 邀请码使用排除易混淆字符的 8 位随机值，可由家庭创建者刷新和作废；
- 图片默认不允许公开索引；
- 不采集手机号、精确位置、健康数据等非必要信息；
- 对 PIN 尝试、邀请码加入和图片上传进行频率和大小限制。

## 12. 验证事件与指标

仅记录验证核心目标所需的数据：

- 打开餐次页面的时间；
- 第一次点菜时间；
- 确认菜单时间；
- 菜单来源：直接点菜、随机或食材匹配；
- 确认后的修改次数；
- 每餐参与成员数和点菜数量。

据此计算：

- 打开到确认的中位用时；
- 通过应用确定菜单的餐次占比；
- 随机和食材匹配的使用率；
- 点菜数量与确认用时的关系；
- 已确认菜单的后续修改频率。

## 13. 测试与验收

### 13.1 自动化测试

- 单元测试覆盖食材同义词、缺失数量、近期降权、随机边界和餐次状态转换；
- 随机算法支持固定种子，保证测试可重复；
- 集成测试覆盖邀请码、PIN、家庭数据隔离、重复提交和并发修改；
- 端到端测试在手机视口完成加入家庭、录菜、点菜、随机、食材匹配和确认菜单。

### 13.2 人工验收

- 在最新两个主版本的移动 Chrome 和 Safari 中完成核心流程，并在平台支持时添加到主屏幕；
- 两台手机可以在同一家庭中完成协作；
- 弱网或短暂断网不会丢失尚未提交的输入；
- 全匹配、缺一种和缺两种食材时结果符合规则；
- 同一道菜被多人点选时正确合并；
- 任一成员均可确认和修改菜单，且修改人显示正确；
- 两周结束时能够导出或查看成功指标。

## 14. 后续候选功能

只有首版验证通过且观察到明确需求后，才考虑：

- 首选标记或每餐点菜数量限制；
- 采购清单；
- 周菜单；
- 长期食材库存；
- 推送通知；
- AI 或图片识别；
- 更强的实时协作；
- 完整菜谱、营养和公开分享。

这些功能不属于当前实施计划范围。
